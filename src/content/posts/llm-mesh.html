A dumb idea

Imagine you are given a 3-D turbulent fluid, a protein folding in water, or a galaxy of colliding dark-matter halos. Classical wisdom says: "Mesh it, build a graph, hand-craft Laplacians, pray your inductive bias is not too wrong." Now, how about we do the opposite and do something that seems completely dumb? How about we flatten the universe into a single sentence, just a list of numbers separated by special tokens, and ask a perfectly ordinary Transformer to predict the next word. No edges, no message passing, no geometric priors. Well, actually, we don't precisely predict the next word; instead, we predict something that looks like the next step in our simulation.

This is a small story about an idea I first thought was fun, then dumb, then amazing, then dumb again. Which is probably a great summary of a PhD yay.

Meshes are actually pretty great. People spent a significant amount of time deciding how to build them, how to ensure they have good properties 1 1 This includes a ton of metrics that you compute for each element of the mesh. Attention as Graph

Now, when you think about it (not too much; it's fairly easy and often used ), a sentence, or at least an ordered list of tokens, can be seen as a fully connected graph. Even more, you can see the attention operation as a message-passing operation. That's why I talked before 3 3 In this article, where I try to study in a graph theory setting a mathematical relation between attention and oversmoothing. 3 In this article, where I try to study in a graph theory setting a mathematical relation between attention and oversmoothing. about the relationship between the number of heads and oversmoothing, because I believe this is one of the reasons for the strength of having more heads in a transformer. Let's throw the sentence away and consider something more complex, such as a set or a .json file. When you think about it, you could also see this as a graph: either as the ordered set of tokens extracted from the .json file, or simply by connecting attributes at the same level together, going one level below as the set gets deeper. That's actually it.

Regression Language Model

This has a nice property: those data structures don't care whether you add an attribute or whether one of the attributes is a list whose length can vary. That's not something you could say if you wanted to represent this set with a fixed-size vector, for example. Meshes and RLM

I've been thinking about different data representations for my meshes since I started my PhD, and I've considered writing them as plain tokens for an LLM for a long time. When I dived into Google's papers, I immediately thought about my project. The first iteration was simple: let's take one node from the mesh, write a JSON file for it, and try to predict its velocity at the next time step. This is how one node was encoded:


{
  "metadata": {
    "simulation": "blood_channel",
    "time_step": 42,
    "dt": 0.001,
    "solver": "navier_stokes",
    "turbulence": false,
    "dim": 3
  },
  "nodes": [
    { "id": 0, "pos": [1.2e-03, 2.5e-04, 9.7e-04], "vel": [1.3e-01, 2.1e-01, 0.0] },
    { "id": 1, "pos": [1.4e-03, 2.8e-04, 1.1e-03], "vel": [1.2e-01, 2.0e-01, 0.0] },
    { "id": 2, "pos": [1.5e-03, 3.0e-04, 1.3e-03], "vel": [1.1e-01, 1.9e-01, 0.0] },
    { "id": 3, "pos": [1.7e-03, 3.2e-04, 1.5e-03], "vel": [1.0e-01, 1.8e-01, 0.0] }
  ],
  "edges": [
    [0, 1],
    [1, 2],
    [2, 3],
    [3, 0]
  ],
  "boundaries": {
    "inlet": [0],
    "outlet": [3],
    "walls": [1, 2]
  }

I then coded a project to teach a small RLM to do precisely that. And it actually works. The performances are not great, but some would call it a proof of concept. I also tinkered a bit with the hop-size information and tracked how performance would improve (or not) if we added more distant nodes to our JSON encoding.

The return of the dumb idea

However, this still begs the question: how on earth do I scale this to a mesh? Yes, sure, for a mesh with a few hundred nodes, I could batch all nodes' JSONs, make my prediction, and then loop over them to predict a trajectory. Yes, I could. But there are at least two large buts here: (i) how will this scale for a mesh with, say, 100k nodes (let's not even think about a 1M-node mesh6 6 Spoiler: not well 6 Spoiler: not well)? (ii) Performances are ok but not great - we probably need to share information between nodes, how do we do that? Well, you can just stack all the inputs together! This is me entering the "this is the worst idea ever" phase. At this point, I stopped working on this project and wrote a short one-pager for students to pick up in January.

Applying the same idea but to molecules

Enter this paper: Transformers Discover molecular structure without Graph Priors, which does exactly what I wanted to try: write a full graph as a list of tokens to predict some molecular attributes. 7 7 molecules have much, much, much fewer nodes than meshes though. 7 molecules have much, much, much fewer nodes than meshes though. And at first, I really liked this paper. Not only was it exactly the idea I wanted to do in the first place, but also, they obtained (i) great results (ii) at great speed (iii) made some nice analysis (for example, the relation between attention and node's position). Now, when you think about it, the paper actually says: let's take a bunch of nodes, write their attributes in a string, and then compute full attention on all tokens. I must admit that, written like that, except to consider it as a thought process or a fun experiment, I'm not so sure about how great my idea actually was.

The return of the great idea

You guessed it, let's write a mesh and the fields that live on it as tokens! I will spare you the details, but I ended up working with something that looks like:


{
"BEG_OF_POS POS_2 ... POS_1 END_OF_POS"
"BEG_OF_VEL VEL_21 ... VEL_13 END_OF_VEL"
"BEG_OF_TYPE TYPE_0 ... TYPE_1 END_OF_TYPE"
"BEG_OF_NEXTVEL TYPE_0 ... TYPE_1 END_OF_NEXTVEL"
}

In comparison to the molecule paper, this is a much more challenging task for a few reasons: - we work with much larger graphs, even though I restricted myself here to meshes with 500 to 2000 nodes. - we need to make an autoregressive prediction 8 8 After predicting the velocity at the next time step, we reuse this as input to make another prediction. We repeat this process for the required number of timesteps. And something great happened: it worked. yay. I trained a transformer with 15 layers of dimension 512, a Gated MLP with an expansion factor of 3, 16 heads per attention layer, and a total of 60M parameters to predict the next-step velocity on 2D meshes representing a flow around a cylinder. Amazing.

Wait, isn't that like a full attention model on some sort of point cloud? I'd say it is.

Now, would we achieve the same results if we apply this to the molecule dataset? I don't know. However, could we achieve the same analysis regarding no inductive bias, reach the same argument regarding speed and kernel optimization, by building a model using flash attention on a point cloud? I would say yes. In conclusion, I'm really unsure about the real impact of such a strategy. Yes, it's fun and interesting. Yes, it's more optimised that sparse GNN operations. But does it really make sense in comparison to a point cloud architecture, I don't think so. As a side note however, this may be a good first project to see if my heads theory on oversmoothing works better on language models than on GNNs directly.
